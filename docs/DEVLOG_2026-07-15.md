## 1. [수정] 보고서 생성 실패 — `embreex` 누락

### 증상
89장 전부 실패, `.twin` 에 카메라 0대:
```
[오류] IMG_1553.JPG: Unable to allocate 575. MiB for an array with shape (75358592,) and data type float64
```

### 원인
**`trimesh` 4.x 는 Embree 바인딩으로 `embreex` 를 찾는다** (`pyembree` 는 trimesh 3.x 시절의 폐기된 이름).
설치돼 있지 않으면 `trimesh.ray.has_embree = False` 가 되어 순수 numpy 브루트포스
(`ray_triangle.RayMeshIntersector`) 로 조용히 폴백한다.

199만 면 메시에 6만 rays 를 쏘면 broad-phase 후보 쌍이 **7,535만 개**로 불어나고,
`trimesh.util.diagonal_dot` 이 그 크기의 1-D float64 배열(= 575 MiB)을 잡으려다 터진다.
(75,358,592 × 8 bytes = 602 MB = 575 MiB — 오류 메시지와 정확히 일치)

> 다른 PC 에서 되던 이유: 거기엔 `embreex` 가 설치돼 있었다. VRAM/RAM 문제가 아니었다.

### 조치
```
pip install embreex
```

### 효과 (실측)
| | 2000 rays 소요 |
|---|---|
| 1회차 | 1.592s ← BVH 빌드(1회성) |
| 2회차 | **0.001s** |
| 3회차 | **0.001s** |

역투영은 더 이상 병목이 아니다. BVH 빌드는 프로세스당 1회라 89장 상각 시 장당 0.02초.

### 남은 할 일
- `README.txt` 의 `pip install` 목록에 `embreex` 가 없다 → 추가함. `rtree` 도 없다(설치돼 있었음).
- `test.py` 가 **`pyembree`** 를 점검한다 → trimesh 4.x 에선 항상 X 로 나오는 무의미한 검사.
  `embreex` 를 보도록 고쳐야 함. (이번엔 미수정)

## 2. [개선] 뷰어 — 핫스팟을 3D 스프라이트로

### 문제
핫스팟 마커가 DOM 요소(`.hud-marker`)라 **깊이 테스트가 없어 메시 뒤에 있어도 그대로 보였다.**

### 시도했다가 버린 방법: 깊이 버퍼 readback
메시 깊이를 저해상도 RT 에 그려 읽어와 마커별로 비교. 검증까지 했으나 **폐기**:

- 정확도는 확보됨: 레이캐스트 정답셋(130개 중 72개 가려짐) 대비
  - 384px RT → 93.8% (7개 오탐)
  - 캔버스 해상도(679px) → **99.2%**
- **그러나 깜빡였다.** 마커 위치는 60Hz 로 갱신되는데 가림 판정은 `OCC_MIN_MS=40` 스로틀 때문에
  25Hz 짜리 묵은 깊이 버퍼를 썼다 → 시점을 움직이면 둘이 어긋나 실루엣 근처가 켜졌다 꺼졌다.

### 채택한 방법: `THREE.Sprite`
레티클을 3D 스프라이트로 만들어 **GPU z-test 가 픽셀 단위로 처리**. 판정이 프레임과 항상 동기라
깜빡임이 구조적으로 불가능하고, readback 도 0.

- 레티클 텍스처: CSS `.reticle`(45° 회전 사각 + 발광 테두리 + 중심점)을 캔버스로 이식 (`makeReticleTex`)
- 심각도 색은 스프라이트별 `material.color` 로 착색. **`NormalBlending` 유지** —
  가산합성은 마커가 겹치면 흰색으로 날아가 "색 = 심각도" 규칙이 깨진다.
- 표면 '위'의 점이라 그냥 두면 자기 표면에 묻힘 → 카메라 쪽으로 거리의 0.4% 당김 (`HOT_LIFT`)
- CSS `hudpulse` 애니메이션 → `updateReticles()` 에서 `material.opacity` 맥동으로 대체
- 리더선 + 태그는 **DOM 유지** (텍스트 선명도·CSS 코너컷 칩). 호버/선택 시 1개만 표시.

### 상호작용
- **호버**: 스프라이트 레이캐스트(쿼드 몇 개라 매 프레임도 쌈)
- **클릭**: 스프라이트가 맞으면 그때만 메시 레이캐스트 → 메시가 먼저 맞으면 무시 (`hotBlocked`)

> 매 프레임 메시 레이캐스트가 불가능한 이유(실측): three.js 는 BVH 없이 전 삼각형을 순회하므로
> **199만 면 메시에 레이캐스트 1회 = 196ms** (130개 = 25.5초). 클릭 1회성이라 감당 가능.

## 3. [개선] 뷰어 — 표시 항목

### 제거
- **이미지 겹쳐 보기** (`ckOverlay`, `showOverlay`/`clearOverlay`, `overlayMesh`, `texLoader`)
- **크랙 중심선(3D)** (`ckLine`, `crackLineGroup`, `crackTubes`, `buildCrackLines`)

> `.twin` 의 `hotspots[].poly` 는 이제 뷰어에서 쓰이지 않는 데이터가 됐다(포맷은 그대로).

### 심각도 색 스케일 재정의 (`sevColor`)
0.1mm(경미·초록) ~ 10mm(심각·빨강) 을 **로그 스케일**로 훑고, `u^0.5` 이징으로
**0.1mm 직후 가파르게 빨개지다 이후 완만**해지게 함.

```
0.1mm → t=0.000    0.32mm → 0.503    1mm → 0.707    3.2mm → 0.868    10mm → 1.000

2배씩 증가할 때 t 변화량:
  0.1→0.2mm : +0.388   ← 가파름
  0.2→0.4mm : +0.161
  1  →2  mm : +0.099
  5  →10 mm : +0.078   ← 완만
```

### 크랙 픽셀(검출 포인트) 가시성
| | 전 | 후 |
|---|---|---|
| 크기 | `modelDiag × 0.0015` | `modelDiag × 0.0045` (`crackRatio`) |
| 색 | 빨강 | **노랑** |
| 모양 | 각진 사각형 | 둥근 점(`makeDotTex`) |
| z-fighting | 표면에 묻힘 | 셰이더에서 `mvPosition.xyz *= 0.996` |

**원인:** `size=0.02` 는 초기값일 뿐 `fitSizes()` 가 `modelDiag × 0.0015` 로 덮어쓰고 있었다.
hammer 모델 대각선이 50.29 단위 → 점 크기 0.075 → **화면상 약 1.0px** = 사실상 안 보임.

`sizeAttenuation:true` 는 **유지** (거리에 따라 작아지는 원근감이 의도된 동작).
UI 에 픽셀 크기 선택(`sizeSelect`) 추가 — 코드 수정 없이 조절 가능.

## 4. [가속] 파이프라인 2.1배

측정 기준: hammer 89장 (5472×3648), RTX 3060 Ti.

### 병목 (최초 실측)
| 단계 | 장당 | 비중 |
|---|---|---|
| 크랙 추론(GPU) | 7.38s | 63.4% |
| 정량화 | 3.09s | 26.6% |
| 역투영 | (1회성 BVH) | — |
| 나머지 전부 | ~0.3s | <3% |

추론 내부: CPU 타일준비 7.0% / **GPU forward 90.6%** / CPU Hann 합성 2.4% → 진짜 GPU 바운드.

### 4-1. `quantify_crack` ROI화 — **18×** (출력 동일)
전체 프레임(2000만 픽셀)에 EDT/skeletonize/label 을 돌리고 있었다. **크랙 픽셀은 2,319개(0.0116%).**
컴포넌트별 bbox 합계 면적은 8.7K 픽셀로 **전체 대비 2,303배 작다.**

컴포넌트끼리는 8이웃 라벨링상 최소 1px 배경으로 떨어져 있으므로, bbox + 패딩(`ROI_PAD=2`)으로
잘라서 처리해도 결과가 전체 프레임과 동일하다.

**검증: 실이미지 6장에서 구/신 출력 대조 → 불일치 0건** (길이·최대폭·평균폭·p95·인스턴스 수·좌표·중심선 전부)

### 4-2. `_order_skeleton` 결정성 — 잠재 버그 수정
ROI 검증 중 `centerline` 만 계속 어긋나서 파보니 ROI 탓이 아니었다:
```python
pts = set(zip(ys.tolist(), xs.tolist()))
start = next((p for p in pts if nc_at(...) == 1), next(iter(pts)))   # ← set 순회 순서
```
`set` 순회 순서는 **튜플 해시 = 좌표값**에 좌우된다. 즉 **같은 크랙이 위치만 달라져도 다른 중심선**이
나왔다(길이가 58 vs 64 pts 로 달라지는 수준). 래스터 순서로 고정해 평행이동 불변으로 만듦.

### 4-3. `cudnn.benchmark = True`
타일 크기가 고정이라 오토튠 결과가 그대로 재사용된다. 출력 중립. 7.38s → 5.44s.

### 4-4. 타일 512→1024, 배치 8→4
```
tile=512  ov=128 : 10×14 = 140장,  36.7M px,  중복도 1.84×
tile=1024 ov=128 :  4×6  =  24장,  25.2M px,  중복도 1.26×
```

배치는 8→4 로 **낮췄다**. 타일이 4배 커져 forward 당 픽셀을 맞추기 위함이며,
처리량은 배치에 거의 무관하다(실측: 타일당 24.93/23.84/25.50/25.63 ms @ batch 4/8/32/48).
**GPU 는 512 타일 하나로 이미 포화** — VRAM 은 8GB 중 0.7~1.4GB 만 쓰고 있었으나
메모리 바운드가 아니라 연산 바운드였다. 배치를 키워도 이득 없음.

|---|---|---|
| 크랙 추론 | 7.38s | **4.56s** |
| 정량화 | 3.09s | **0.19s** |
| **이미지당** | **~10.8s** | **~5.0s** |
| **89장** | **~16.0분** | **~7.5분** |

## 5. ⚠️ 판단이 두 번 뒤집힌 경위 (중요)

타일 설정 변경(512→1024)을 **처음엔 "검증 불가"라며 기각했다가, 실제 콘크리트 이미지 1장으로 뒤집었다.**
같은 함정을 다시 밟지 않도록 남긴다.

### 오판 ①: "타일이 클수록 정확하다"
FCN 이니 타일이 클수록 '타일 없는 전체 추론'에 가까워 더 충실할 것이라 가정했다. **틀렸다.**
`network/_deeplab.py` 의 ASPP 에는 **`AdaptiveAvgPool2d(1)` 전역 풀링 브랜치**가 있다:
```python
class ASPPPooling(nn.Sequential):
    def __init__(...):
        super().__init__(nn.AdaptiveAvgPool2d(1), ...)   # 입력 전체를 1×1로 평균
    def forward(self, x):
        return F.interpolate(super().forward(x), size=x.shape[-2:], ...)   # 전체에 broadcast
```
즉 **한 픽셀의 출력이 "그 픽셀이 속한 타일 전체의 평균"에 의존**한다. 타일 크기 = 전역 문맥 창이고,
모델은 그 창 크기에 맞춰 학습됐다. 전체 추론은 '진실'이 아니라 학습 때 본 적 없는 **분포 밖 입력**이다.

> `nn.Linear` 가 없다는 것만 확인하고 ASPP 내부를 안 본 채 추론한 결과. 아키텍처는 끝까지 봐야 한다.

### 오판 ②: "hammer 로 재보니 위험하다"
hammer 로 측정해 **IoU 0.58 · 최대폭 +11.67%** 가 나오자 기각했다. **그 측정 자체가 무효였다.**

**hammer 는 콘크리트가 아니라 책상 위 물체(망치 등)를 찍은 데이터다.** 거기 잡히던 "크랙"은
전체 픽셀의 0.01~0.06% 짜리 **허위 검출(노이즈)**이었다. 경계선상의 불안정한 검출이라
설정만 바뀌면 쉽게 뒤집힌다 → 변화량이 크게 나온 것.

### 실제 콘크리트로 재측정한 결과
| | 크랙px | 인스턴스 | 최대폭 | 엄격 IoU | **±1px 허용 IoU** |
|---|---|---|---|---|---|
| 512/128 (기준) | 32,531 (1.175%) | 42 | 8.9px | — | — |
| 512/64 | 32,247 (1.165%) | 47 | 8.9px | 0.9028 | **0.9920** |
| 768/128 | — | — | — | 0.8776 | **0.9909** |
| **1024/128** | 32,040 (1.157%) | 46 | 8.5px | 0.8573 | **0.9914** |

- 실제 크랙은 픽셀 밀도가 **1.175%로 100배 조밀**하고 검출이 강건하다.
- **크랙 두께 중앙값이 2.8px** → IoU 가 가혹한 지표다. 경계 1px 흔들림만으로 엄격 IoU 가 0.86 까지 빠진다.
  **±1px 허용 시 전부 0.99+** = 사실상 동일. 오버레이도 육안으로 구분되지 않았다.

### 교훈
- **도메인 밖 데이터로 잰 변화량은 의미가 없다.** 노이즈의 변화량을 재고 있었던 셈.
- 가는 구조(2.8px)에 엄격 IoU 를 쓰면 과잉 반응한다. 허용오차를 함께 봐야 한다.
- hammer 는 이 프로젝트의 검증 기준으로 부적합하다.

### 이번 검증의 한계
근거는 **stock 사진 1장(1920×1442, 레이블 없음)**이다. 실제 촬영본은 5472×3648 이라 타일 배치가 다르다.
**실제 촬영한 콘크리트 사진 몇 장으로 재확인 권장.**

## 6. 미해결 이슈

### 6-1. ⚠️ 크랙 실척이 1000배 어긋난 것으로 의심
`hammer.twin` 실측:
```
width_mm_max : 22.2 ~ 871.7 mm      ← 크랙 폭 871mm?
length_mm    : 24.3 ~ 17,471.6 mm   ← 길이 17.5m?
sevColor 임계 : 0.1 ~ 10 mm
```
130개 핫스팟 **전부 최고위험(빨강)**으로 칠해진다. `build_scale_map` 의 `med_depth/fx*1000.0` 이
**"PLY 1단위 = 1m"** 가정에 의존하는데, 포토그래메트리 메시가 실척으로 정규화돼 있지 않으면 그대로 깨진다.
(hammer 가 애초에 콘크리트가 아니라는 점도 겹침) **실제 콘크리트 촬영본으로 보고서를 만들어 확인 필요.**

### 6-2. `.twin` 용량이 PLY 에 선형 비례 — 상한 없음
```
.twin 크기 ≈ 1.33 × (PLY 바이트) + 0.43MB × (이미지 장수)
```
실측 검증: hammer = 1.33×62MB + 0.43×89 = **예상 120.9MB vs 실제 128.2MB**

이미지는 장당 상한이 있으나(`FULL_MAX_PX=1920` q82 → 0.340MB, `THUMB_MAX_PX=900` q75 → 0.090MB),
**`mesh_base64` 는 상한이 없다.**

`reports/1234.twin` = **1.6GB 인데 `cameras: []`, `hotspots: []`** — 위 embreex 버그로 전멸한
**빈 껍데기**다. 게다가 `viewer.html` 은 `const DATA = __DATA__;` 로 .twin 전체를 JS 소스에
인라인하므로, 수백 MB 급 보고서는 브라우저 문자열 한계에 걸려 **열리지도 않을 가능성이 높다**(미검증).
`reports/` 전체가 1.7GB 로 리포지토리 용량의 대부분을 차지한다.

### 6-3. 기타
- **Git 저장소가 아니다.** 1.7GB `reports/` 를 커밋하지 않도록 `.gitignore` 부터 만든 뒤 `git init` 권장.
- `test.py` 가 `pyembree`(폐기된 이름)를 점검 → `embreex` 로 수정 필요.
- `viewer.html` 의 `.hud-marker.active` 에 `high` 클래스 검사가 있으나 **어디서도 추가되지 않는 죽은 코드.**
- 기존 `.twin` 들은 `tile=512` 로 생성됨 → 재생성 시 수치가 미세하게 달라진다.
