### 수정
- **배포 앱에서 사진 몇 장 만에 메모리가 고갈되던 문제 (embree 누락)** — 번들에 embreex 의 Cython 모듈
  `rtcore` 와 dist-info 메타데이터가 빠져 `import embreex` 가 실패했고, trimesh 는 조용히 numpy 광선 교차
  (`ray_triangle`)로 물러났다. 이 경로는 광선마다 전 삼각형 배열을 만들어 3천만 면 메시에서 장당 수십 GB 를
  먹는다(실측: 커밋 111GB, 사진 5장째부터 "Unable to allocate", 크랙 0개 보고서). `build.py` 에
  `--collect-all embreex --copy-metadata embreex` 를 넣고, 파이프라인은 교차 엔진 이름을 로그에 찍고
  embree 가 아니면 즉시 오류로 멈춘다. `크랙 디지털 트윈 스튜디오.exe --selftest` 가 번들 자가진단
  (torch CUDA·embree·모델 등)을 exe 옆 `selftest.txt` 에 남긴다 — 배포 전 확인용.
  분석 로그의 장별 줄에 메모리 사용량을 붙였다. 디버그용으로 `/api/create` 가 `limit`(사진 수)을 받는다.
- **요약 타일(코스 LOD)의 구멍 제거** — 멀리서 볼 때 돔이 점·선투성이로 보이던 문제. `tiler.simplify` 가
  3-클리크에 칸별 부채꼴(dual fan) 삼각형과 작은 경계 고리 메움을 더해, 돔 영역 배경 픽셀이 보통 LOD 에서
  원본 잎 타일과 같은 수준(24.5%)이 됐다(종전 25.1%, 루트 34.5%→27.1%). 아래 벽의 검은 선은 원본 스캔의
  빈틈이라 그대로다. `docs/DEV_LOD.md` §2.

### 추가
- **분석 진행 로그·전체 진행률** — 6GB 메시에서 메시 읽기·embree 가속 구조·타일 생성처럼 로그가
  몇 분씩 멈추는 구간이 있어 진행 여부를 알 수 없었다. `pipeline.Progress` 가 7단계 가중치로 전체 %를
  만들어 대시보드 막대와 로그("▶ [전체 NN%] (k/7) 단계", "[전체 NN%] 단계 NN% · 세부 · 메모리")에
  같이 보이고, 20초 이상 조용하면 심장박동("진행 중 · N초 경과")을 찍는다. 타일러도 읽기/정렬/타일 생성
  진행을 같은 형식으로 보고한다.
- **측정용 메시를 옥트리 컷으로** — trimesh 가 1억 9천만 면을 통째로 들면 20GB 를 넘어 MemoryError.
  타일을 먼저 만들고 그 옥트리 컷(약 3cm 요약, 면 2천만 이하)을 역투영에 쓴다(`MEASURE_MAX_FACES`).
  report_meta 에 `measure_faces`·`measure_cell_m` 기록. 상세는 `docs/DEV_LOD.md` §2-1.
- **계층 LOD 타일 — 6GB 메시 지원** — 원전 촬영본 PLY(6.26GB · 정점 9,628만 · 면 1억 9,247만)로
  만든 보고서가 열리지 않던 문제. 뷰어가 `mesh.ply` 를 통째로 받던 구조를 버리고, 생성 시
  `tiler.py` 가 메시를 옥트리 타일(잎=원본, 내부=격자 병합 요약)로 쪼개 `tiles/<id>.bin` 에
  넣는다. 뷰어(`ui/tiles.js`)는 절두체 안 타일만 화면 오차(px) 기준으로 골라 스트리밍·교체·해제하고
  화면 삼각형 예산(500만)을 넘으면 문턱을 스스로 올린다. 클릭·측정(`pickMesh`)은 그려지는 타일에만
  BVH 를 지연 생성해 처리한다. 옛 보고서(`mesh.ply`)는 간략 메시 + 원본의 두 단계 타일셋으로
  같은 경로에서 열린다. `tools/compare_twins.py`·`tools/export_report.py` 는 `tools/twin_mesh.py`
  로 정점 표본을 타일에서 읽는다. 원점 이동은 `ui/origin.js` 로 분리(타일 보고서는 meta 만 옮김).
  실측: 타일 7,071개 · 14.4분 · 결과 4.09GB(종전 6.9GB) · 루트 즉시 표시 · 클릭 62ms.
  설계·처리 순서·수정 지점은 `docs/DEV_LOD.md`, 포팅 기록은 `docs/PLAN_LOD_PORT.md`.
- **폴더 배포 빌드 (`build.py`)** — `py build.py` → `dist/크랙 디지털 트윈 스튜디오/` (PyInstaller
  `--onedir`, torch CUDA 포함이라 수 GB). `app.py` 에 WebView2 런타임 확인·아이콘·오류 안내창을
  넣었고, `backend.py` 는 exe 실행 시 보고서를 exe 옆 `reports/` 에 둔다.

### 수정
- **3D 표면이 계단처럼 층져 보이던 문제 수정 (뷰어 좌표 원점 이동)** — PLY 와 meta 는
  UTM 절대좌표(예: Y≈4,113,800)를 double 로 담는데 three.js 는 위치를
  `Float32BufferAttribute` 로만 GPU 에 올린다. float32 의 눈금 간격은 값 크기에 비례해
  Y≈4.11e6 에서 **0.25 m**, X≈3.0e5 에서 0.031 m — 삼각형 변(≈57 mm)보다 큰 단차라
  표면이 한 방향으로 층지고 크랙 튜브 중심선까지 밀렸다.
  실측(100MEDIA, 정점 200만): float32 Y 고유값 **1,607개**뿐(= 계단 1,607층),
  벽면 평면 잔차 14.8 → 46.9 mm, 리본 중심선 변위 중앙 98.7 mm(튜브 반경의 5.2배),
  카메라 위치 중앙 64 mm.
  이제 메시 바이너리(`plyVertexLayout`/`plyOrigin`/`plyShift`)와 meta 좌표
  (`cameras[].pos` · `ribbons[].poly` · `hotspots[].xyz` · `text_points`)에서 공통 원점을
  빼 국소좌표로 그린다 — 눈금 0.25 m → **0.0038 mm**, Y 고유값 1,607 → 1,848,060.
  200만 정점 이동에 21 ms.
  **.twin 파일은 바뀌지 않는다** — 메모리 안에서만 옮기므로 기존 보고서가 그대로 열리고,
  파이프라인의 mm 측정값(trimesh, float64)은 애초에 영향을 받지 않았다.
  화면·CSV 에 좌표를 내보내는 자리(`camCoord` · 크랙 패널 · crack_list.csv)는 `wpt()` 로
  원점을 다시 더해 **표기값은 종전과 동일**하다. 검사 비교의 이전 검사 고스트는 정합 행렬에
  원점 이동을 이어붙여(`M.premultiply`) 같은 좌표계로 맞춘다.
  절대좌표가 작거나(±1024 m 이내) 해석할 수 없는 PLY 형식이면 이동을 건너뛴다(종전 동작).
- **긴 크랙의 대표 뷰 실패 수정** — 대표 뷰 선택이 크랙 중심점 하나의 가시성만
  검사해서, 여러 뷰에 걸친 긴 크랙은 중심점이 어느 멤버 뷰 화면에도 안 들어가
  엉뚱한 중앙 크롭으로 떨어졌다. 중심선 커버리지(가장 많이 보는 뷰) 기준으로
  교체하고, 크롭도 그 뷰에 보이는 구간의 중앙에 맞춘다. 부분만 보이면
  "크랙의 N% 구간" 을 라벨에 표기.
- **세로 촬영 이미지 180° 뒤집힘 수정** — 이미지 방향을 종횡비로 추측하던 로직이
  90° 시계/반시계를 구분하지 못해(회전 후 모양이 동일), EXIF ori=8 사진이 보정
  기준으로 180° 뒤집힌 채 분석되던 문제(실측: interior 데이터셋 391장 중 172장 —
  전 검출이 엉뚱한 3D 위치로 역투영됨). `load_oriented()` 가 치수 근거로 판정하도록
  교체: calib==원시 치수면 원시 그대로(Zephyr 는 EXIF 를 무시하고 보정),
  calib==EXIF 적용 치수면 태그 그대로 적용(방향 모호성 없음).
  ⚠ 세로 사진이 섞인 기존 보고서는 재분석해야 한다.
- **추론 캐시의 방향 오염 차단** — 캐시 키에 방향 판정 태그를 추가. 같은 파일·같은
  치수라도 방향 로직이 바뀌면 픽셀 배치가 180° 다른데 키가 같아서, 위 수정 직후
  구 방향에서 만든 확률맵이 그대로 히트해 마스크가 어긋나는 것을 검증 중 발견.
  구 캐시는 키가 달라져 자동 무효화된다(재추론).

### 변경
- **폭 측정 1차 소스를 3D 엣지 쌍 실측으로 승격** — 기존 스케일맵(z/fx×1/cosθ) 곱은
  광선 오착지 시 조용히 폭주했고(실측: 픽셀폭 2px 균열이 444mm 로 보고) 등방 cosθ
  근사였다. 좌·우 경계 역투영 |L3d−R3d| 를 깊이 일치 게이트 2종(좌우 착지 깊이차 ·
  쌍 깊이 vs 중심선 중앙 깊이)으로 걸러 1차 소스로 쓴다 — 오착지가 '조용한 25cm'가
  아니라 '명시적 측정 실패'가 된다. 유효 표본 부족 시 스케일맵 폴백(width_src="2d",
  국소 스케일 3×중앙 초과점은 무효화). 두 방식이 1.3× 이상 다르면 width_flag.
  검증(interior 오염 이미지 11장): 444mm 균열 → 중앙 10mm 로 정상화, 남은 대형
  max 는 게이트 통과한 '실제로 넓은 어두운 영역'(blob 오탐)으로 유형 분류가 담당.
  전 규모 검증(interior 391장, 구 알고리즘 보고서와 동일 조건 대조):
  3D 소스 채택 1,826/1,828(99.9%) · p95폭 중앙 4.55→3.62mm(−20%) ·
  max>100mm 33→22개(−33%) · **심각도 S6(특이값) 341→243(−29%)** — 분포 전체가
  아래로 이동(cosθ 과보정·오착지 인플레이션 제거). p95폭 상위는 전부 joint/blob
  오탐으로 재편(crack형 >50mm 는 926개 중 3개), 검출·병합·정합 진단은 완전 동일
  (결정성 재확인). 잔여: 방식 불일치 플래그 37% — 임계(1.3×) 조정 후보.

### 추가
- **뷰 간 정합 오차 자기진단** — 병합 단계에서 같은 균열의 뷰별 중심선이 3D 에서
  어긋난 거리(중앙·p90 mm)를 실측해 `report_meta` 에 기록하고 뷰어 요약에 표시.
  병합 eps 의 3/4 를 넘으면 경고(⚠), 서로 3×eps 안까지 접근한 크랙 쌍은
  "조각남 의심"으로 집계 — "포토그래메트리가 부정확하면 측정이 무너지는가"에
  보고서마다 숫자로 답하는 장치. (폭·길이는 δz/z 비율 오차라 정합에 둔감하고,
  병합·신원이 임계값 기반이라 취약 — 그 취약 지점을 감시한다.)
- **크랙 튜브 실폭(×1) 표시** — 튜브 지름 = 측정 폭(기본값). 기존에는 최소 반경
  2cm + 2배 과장이라 0.3mm 균열이 4cm 튜브로 그려져(130배) 실제 폭을 오도했다.
  표시 메뉴의 토글로 강조(과장) 모드와 전환 가능(localStorage 기억).
  실폭 모드는 표면 위 6cm 띄우던 오프셋도 반경에 비례하도록 줄여 표면에 얹힌 듯
  보인다. 호버·클릭은 화면 14px 히트박스라 굵기와 무관하게 동작.
- **측정 바닥(분해능 한계) 표기** — 파이프라인이 균열마다 대표 뷰의 GSD(`gsd_mm`)를
  기록하고, 폭이 2×GSD 미만이면 뷰어·PDF 가 "≤상한" 으로 검열 표기한다.
  분해능 밖에서 잰 값을 정밀한 실측처럼 보이게 하던 가짜 정밀도를 제거.
- **뷰 간 산포 불확실도(±)** — 같은 균열을 3장 이상에서 검출하면 뷰별 폭의
  IQR/2 를 `w_unc_mm` 로 저장하고 뷰어·PDF 대장(± 열)에 표기.
- **캘리브레이션 영속화** — 뷰어 2점 캘리브레이션을 사이드카
  (`<twin>.review.json` 의 `calib`)에 저장(`POST /api/calib`). PDF 가 같은 보정을
  모든 수치·심각도에 적용하고 표지에 계수를 명시. 구버전 localStorage 값은
  부팅 시 1회 자동 마이그레이션.
